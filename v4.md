# Cursor Rules – Python 3.14 Projects

## 0. Scope and Assumptions

- These rules apply to all Python code in this repository.
- Assume the project targets **CPython 3.14**.
- Prefer to keep code compatible with Python 3.13 when it is easy to do so.
- If existing code clearly follows a different convention, prefer **consistency with the existing codebase** unless the user explicitly asks to modernise or refactor.

---

## 1. Environment, Tooling & Dependency Management

### 1.1 Package and environment management

- Always use **`pyproject.toml`** as the single source of truth for:
  - Build backend and metadata.
  - Runtime dependencies.
  - Tool configuration (formatter, linter, type checker, pytest, etc.).
- Respect any existing tool choice:
  - If the project is already using `uv`, Poetry, PDM, or plain pip, follow that choice.
  - Do **not** introduce a second package manager without explicit user approval.

### 1.2 Greenfield default

- For new projects (no existing choice visible):
  - Default to **`uv`** for dependency and environment management.
  - Create and maintain:
    - `pyproject.toml`
    - `uv.lock`
- If the user explicitly prefers **Poetry**:
  - Use Poetry with:
    - `pyproject.toml`
    - `poetry.lock`

### 1.3 Lockfiles and reproducibility

- **Lockfiles are mandatory** for any non‑trivial project:
  - `uv.lock` for uv.
  - `poetry.lock` for Poetry.
  - For pip‑only projects:
    - Maintain a fully pinned lock file:
      - Either a dedicated `requirements.lock` or
      - A fully pinned `requirements.txt` generated by a tool like `pip-compile`.
- Rules:
  - Always **commit lockfiles**; they must not be in `.gitignore`.
  - Never manually edit lockfiles; they should be generated by the package manager.
  - Treat “lockfile + `pyproject.toml`” as the canonical definition of dependencies.
- When editing dependencies:
  - Update `pyproject.toml`.
  - Regenerate the lockfile with the appropriate command (`uv lock`, `poetry lock`, or equivalent).
  - Do not add dependencies only in the lockfile or only in a side file.

### 1.4 Tools

Unless the project already specifies others:

- **Formatter**: `black` (or Ruff’s formatter if already in use).
- **Linter**: `ruff`.
- **Type checker**: `mypy` (or `pyright` if already set up).
- **Tests**: `pytest`.

Configuration guidelines:

- Prefer `pyproject.toml` for tooling config:
  - `[tool.black]`
  - `[tool.ruff]`
  - `[tool.mypy]`
  - `[tool.pytest.ini_options]`
- Add any tool caches or build artefacts (e.g., `.ruff_cache`, `.mypy_cache`) to `.gitignore`.

## 2. File & Directory Naming

- Python files and packages:
  - Use `snake_case` for modules and package directories.
  - Examples:
    - `user_service.py`
    - `data_loader.py`
    - `config_manager.py`
  - Avoid vague names like `misc.py`, `helpers.py`, `stuff.py`.
- Packages:
  - Package directories should also be `snake_case`.
  - Every package directory must contain an `__init__.py`.
- Tests:
  - Test modules must be named `test_<thing>.py` (e.g. `test_user_service.py`).
- Entry points / CLIs:
  - Use clear names such as:
    - `main.py`
    - `cli.py`
    - `train_model.py`
    - `sync_data.py`
- Scripts and tooling:
  - Place one‑off or admin scripts under `scripts/` with descriptive names:
    - `scripts/backfill_orders.py`
    - `scripts/reindex_search.py`

Rules:
- All importable application code lives under `src/<package_name>/`.
- Do not add new importable modules at repository root.
- Place new code into an existing package structure when it fits.
- Keep directory nesting shallow; avoid deep hierarchies unless clearly justified.

## 4. Architecture, Concurrency & Async Strategy

### 4.1 Layered architecture

Use a layered architecture with clear boundaries:
- **Domain layer:**
  - Pure business rules and domain models (`models/`, domain services).
  - No knowledge of frameworks, databases, HTTP, or CLI.
- **Application / service layer:**
  - Use‑cases and orchestration (`services/`).
  - Coordinates domain objects, I/O, and infrastructure.
- **Infrastructure / data access layer:**
  - Implementations of persistence and I/O (`repositories/`, external APIs, filesystem).
- **Interface / presentation layer:**
  - HTTP APIs, CLIs, message consumers, schedulers (`api/`, `cli/`, etc.).

Import direction:
- Interface → Application → Domain.
- Infrastructure → Domain where needed.
- Domain must not import Infrastructure or Interface.

Use dependency injection:
- Pass repositories, clients, configuration, and other collaborators into services and functions.
- Avoid global singletons and module‑level mutable state.

Keep domain logic as pure as practical:
- Business rules should be mostly pure functions/methods.
- I/O and side effects belong at the edges (infrastructure or thin services).

### 4.2 Async/await strategy

Python 3.14 is strongly optimized for async; follow an “async by default for I/O” rule:

- **For I/O‑bound and network‑heavy services** (e.g., web APIs, message processors):
  - Prefer async frameworks and libraries (e.g., async HTTP frameworks, async DB clients).
  - Design service and repository interfaces around `async def`.
- **For CPU‑bound tasks:**
  - Keep core computation synchronous.
  - Offload them from async event loops via `asyncio.to_thread` or process pools.
  - Do not block the event loop:
    - Avoid direct use of blocking I/O (e.g. plain `requests`, blocking DB drivers) in `async def`.
    - If blocking libraries must be used, isolate in a dedicated sync layer and call via `to_thread` or a worker process.
  - **Use structured concurrency:**
    - Prefer `asyncio.TaskGroup` (or framework‑equivalent patterns) for managing concurrent tasks.
    - Cancel tasks cleanly and ensure proper teardown of resources.

Migration rules:
- **If the project is entirely synchronous today:**
  - Do not autoconvert large swathes of code to async without explicit instruction.
  - For new I/O‑bound components, consider async, but keep the overall style consistent unless the user approves a broader shift.
- **For mixed codebases:**
  - Keep boundaries clean: async interfaces at the edges, clear sync wrappers where needed.

### 4.3 Threads, multiple interpreters and no‑GIL

- **Do not assume the GIL guarantees safety** for shared mutable state:
  - Use appropriate synchronization (locks, queues, etc.) or confinement to a single thread.
  - Prefer message passing and immutable data structures.
- **For code designed to benefit from no‑GIL / free‑threaded Python:**
  - Avoid global mutable state.
  - Ensure C extensions in use are thread‑safe or documented as compatible with no‑GIL builds.
- **If using multiple interpreters:**
  - Treat each interpreter as an isolated runtime.
  - Pass data via serialization (JSON, msgpack, pickles with care).
  - Keep interpreter boundaries narrow and explicit.

## 5. Code Style, Typing & Type Checking Strictness

### 5.1 Style

- Follow PEP 8:
  - `snake_case` for functions and variables.
  - `PascalCase` for classes.
  - `CONSTANT_CASE` for module constants.
- Imports:
  - Group imports as: stdlib → third‑party → local, separated by blank lines.
  - Avoid `from module import *`.
  - Keep imports at top of files; use local imports only to avoid heavy or circular imports.
- Logging:
  - Use the `logging` module instead of `print` in libraries and production code.
  - `print` is acceptable only in small scripts or CLIs and should be obvious.

### 5.2 Type hints

- All new public functions, methods, and class attributes must have type hints.
- Prefer explicit return types even when a tool could infer them.
- Use `typing` (and `collections.abc` for protocols) for standard types.
- Use `typing_extensions` only when types are not yet available in the standard library.

### 5.3 Annotations and reflection

- Treat annotations as lazily evaluated (Python 3.14 deferred annotations / PEP 649).
- For reflection or runtime inspection:
  - Prefer `typing.get_type_hints()` or `annotationlib` helpers rather than reading `__annotations__` directly.
  - Do not rely on annotations being plain values stored statically; always use the supported APIs.

### 5.4 Strict type checking

**For greenfield or type‑clean modules:**
- Default to strict type checking:
- In `pyproject.toml` (mypy example):
    ```toml
    [tool.mypy]
    python_version = "3.14"
    strict = true
    ```
- For `pyright`, use strict mode (config or `# pyright: strict` where appropriate).

**For legacy or partially typed code:**
- Do not disable strict checking globally just to accommodate untyped modules.
- Instead:
  - Use per‑module overrides in `mypy.ini` or `pyproject.toml` (`[[tool.mypy.overrides]]`) to gradually adopt strictness.
  - Tighten strictness incrementally (e.g., enable `strict = true` for new and refactored modules).
- **Rules in CI:**
  - Treat type checking failures like test failures: they must be fixed or explicitly justified.
  - Avoid sprinkling `# type: ignore` liberally; where required, prefer `# type: ignore[code]` with a short comment.

## 6. Tests

- Use `pytest` as the default test framework.

### 6.1 Layout

```text
tests/
  unit/
    test_<module_or_feature>.py
  integration/
    test_<system_or_boundary>.py
  # optional:
  e2e/
```

Rules:
- Test files: `test_*.py`.
- Test functions: `test_<behavior>` naming.

### 6.2 Testing practice

- For every new feature or bugfix, add or update tests that cover the behaviour.
- Prefer small, focused tests that assert one behaviour at a time.
- Tests must be deterministic:
  - Avoid reliance on real time, global state, or external services.
  - Use fixtures for setup instead of copy‑pasted code.
- External services:
  - Use mocks, stubs, or local test doubles instead of real external APIs.
  - For databases, use temporary or in‑memory databases where possible.
- Async code:
  - Use pytest’s async support (`pytest-asyncio` or framework‑specific plugins) for async tests.
  - Test concurrent behaviours (e.g., with `TaskGroup`) to catch race conditions or ordering issues.

  - Use imperative mood in the subject line:
    - "Add user registration endpoint"
    - "Fix payment validation"
    - "Refactor repository layer"
  - Add a brief explanation in the body for non‑trivial changes.
- Commits:
  - Group logically related changes.
  - Avoid mixing large refactors with unrelated functional changes.
  - Do not commit generated files, build artefacts, caches, or local configuration.
- Branch naming:
  - Use clear prefixes:
    - `feature/<short-description>`
    - `fix/<short-description>`
    - `refactor/<short-description>`

### 7.2 CI

  - Formatter (black or Ruff’s formatter).
  - Linter (ruff).
